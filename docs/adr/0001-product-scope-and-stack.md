# ADR-0001：产品范围与技术底座

- 状态：已接受（默认决策，可复审）
- 日期：2026-11-02
- 决策人：项目负责人（默认授权执行）
- 关联：[PRD v0](../product/PRD-v0.md)、[90 天技术路线](../product/90-day-roadmap.md)

## 背景

现有仓库是一个可复跑的电商客服/导购 Agent 原型：规则意图、确定性工具、双时态知识库、生成前合规门禁、哈希链审计、170 条离线评测。它证明了「机制正确性」，但没有真实交易、真实用户、支付/退款、后台审批和运营闭环。

下一阶段的目标不是作品集，而是一个真实产品：用完整电商系统作为载体，锻炼从领域建模、交易一致性、权限安全、可观测性到产品判断的能力。约束是单人开发、预算有限、不能长期闭门造车。

## 决策

### D1. 首个产品：单商家 3C 配件店 + AI 售后运营台

- 首版只做单商家、单币种（CNY）、单仓库、20–50 个 SKU。
- 所有业务表带 `merchant_id`，为未来多租户留位，但首版不做多租户逻辑。
- 选择 3C 配件的原因：现有种子数据、政策库和团队背景最接近；售后问题类型清晰（物流、退换、保修、价保）。
- 可改成本：换类目只改种子、政策与文案，不改架构；如果换到生鲜/服饰，需要重新定义退货与库存规则。

### D2. 自建模块化单体，不以 Medusa/Saleor/mall 为底座

- 自建商品、库存、购物车、订单、支付、售后、提案/审批。
- 采用模块化单体：一个后端部署单元 + 一个 worker + 一个 Next.js 应用；不拆微服务。
- 原因：
  1. 目标是学习完整交易系统与领域建模，直接套底座会把最想学的部分外包掉。
  2. 现有门禁/审计/评测需要深度嵌入交易流程，跨系统改造反而更贵。
  3. 单人维护，单体 + 清晰模块边界比分布式更可靠。
- 代价：要自己处理库存一致性、支付幂等、退款对账、权限与审计；首版功能速度慢于套用 Medusa。
- 备选：
  - Medusa 2.x（MIT，Node/TS）：冷启动最快，但交易核心不是自己的，且引入 Node + Python 双栈。
  - Saleor（BSD-3，Python/GraphQL）：语言契合，但 GraphQL + Postgres/Redis/worker 运维更重。
  - macrozheng/mall（Apache-2.0，Java）：中文商城完整，但基础设施重、代码量大、AI 非原生。
- 复审触发：如果 90 天内交易底座开发超过 6 周仍无法跑通下单/支付/退款，考虑改用 Medusa/Saleor 做底座，把精力集中在 AI 治理层。

### D3. 技术栈：Python/FastAPI + PostgreSQL + Next.js

- 后端：Python 3.12、FastAPI、Pydantic 2、SQLAlchemy 2、Alembic。
- 数据库：PostgreSQL 16+；金额整数分；JSONB 存提案 payload；FTS/pgvector 后续按需。
- 前端：Next.js（最新稳定版）+ TypeScript + 自定义 CSS；一个应用承载店面、后台、聊天窗。
- 队列：首版 Postgres Outbox + worker；不引入 Redis/RabbitMQ/Kafka，直到指标证明需要。
- 支付：自建 mock PSP（支付单 + 签名 webhook + 幂等账本）；拿到资质后接真实沙箱。
- AI：保留现有 provider 抽象（template/ollama/openai）；显式 tool-calling 循环；不引入 LangChain/Dify 作为编排核心。
- 原因：最大化复用现有 Python 资产；Postgres 一个数据库覆盖事务、JSON、检索；Next.js 一套前端覆盖三种界面；单体降低运维与调试成本。
- 代价：Python 在高并发交易场景不如 Go/Java；Next.js 需要学习 React/TS；单库在规模上来后需要读写分离/分区。
- 复审触发：API p95 持续超过目标、单库 CPU 饱和、团队超过 2 人、需要独立前端团队。

### D4. AI 权限边界：只读自由，写操作只能提案

- AI 可自由调用只读工具：商品、订单、物流、政策、售后状态。
- 资金/状态变更（退款、补偿、改地址、取消订单）只能创建 `action_proposals`，由人工批准后执行。
- 高危意图（退款确认、赔偿、价保、投诉）只解释不确认；每轮必须有真人入口。
- 所有回复必须带政策引用（或明确未查到）、数字溯源、审计 ID。
- 首版不做自动审批；未来如做，必须限额、抽检、可回滚，并单独写 ADR。
- 原因：这是现有项目最强的差异化，也是商家最真实的顾虑；直接让 AI 写资金动作不可接受。

### D5. 支付与资金：首版 mock，不接真实资金

- 自建 mock PSP：创建支付单、跳转支付页、签名 webhook、幂等回调、账本记录。
- 退款也走 mock：批准后记账，状态回写；不产生真实资金流。
- 原因：真实支付需要资质、合规、对账、风控；在需求未验证前接入是浪费。
- 复审触发：至少 3 个商家愿意付费试点，且明确要求真实支付；届时单独评估 Stripe/支付宝/微信沙箱与合规成本。

### D6. 部署：Docker Compose + 单台 VPS

- 本地与首版生产都用 Docker Compose：postgres、api、worker、web、Caddy。
- 不引入 K8s、服务网格、Terraform（除非出现多环境/多团队需求）。
- 备份：每日 pg_dump；每月恢复演练。
- 原因：单人可维护；先把系统跑稳，再谈弹性。

## 影响

### 正面

- 交易、AI 治理、审计在同一代码库内，端到端可控。
- 可以按学习节奏深入数据库、事务、状态机、权限、支付、可观测性。
- 不被第三方电商平台的边界绑死；未来可长成多租户 SaaS 或开源自托管。
- 现有门禁/审计/评测资产可复用，不用从零开始。

### 负面

- 首版开发量明显大于套用 Medusa/Saleor。
- 需要自己承担库存一致性、支付幂等、退款对账、安全等高风险模块。
- Python/Next.js 双语言；单人需要同时维护后端、前端、运维。
- 没有真实商家时，容易闭门造车；必须用访谈/试点约束需求。

## 复审触发条件

满足任一条件就重新评估本 ADR：

1. 90 天内无法完成「下单 → mock 支付 → 订单 → 售后提案 → 审批」闭环。
2. 交易底座开发超过 6 周，且没有可用的真实订单。
3. API p95 持续超过目标 2 倍，或单库成为明确瓶颈。
4. 商家明确要求接入其现有电商平台（Shopify/有赞/微店等），自建交易底座不再是优势。
5. 需要多租户/多仓库/多币种，单体边界开始失控。
6. 团队扩大到 3 人以上，需要独立部署与分工。
