# 服务编排说明（一键启动 / 一键停止）

本项目的运行形态是一个**单进程 HTTP 服务**（`python -m src.server`）+ **两个 SQLite 文件**
（合成店铺库、审计库），外加一个**可选的外部进程**（本机 Ollama）。编排器负责这几样的
预检、按序启动、健康确认、优雅停止与残留回收。

> 边界先说清：这是作品集原型的服务管理，**不是生产级 supervisor**——不做守护重启循环、
> 不做开机自启、不做多机部署。为什么不做，见文末「有意不做的三件事」。

---

## 一、命令清单

| 命令 | 作用 | 退出码 |
|---|---|---|
| `python -m ops.cli check` | **只预检**，不动任何进程；同时打印当前状态 | 0 无阻塞项 / 1 有阻塞项 |
| `python -m ops.cli start` | 一键启动：预检 → 若已在运行则**先全部停止** → 按依赖顺序启动 → 逐个健康确认 | 0 成功 / 1 失败 |
| `python -m ops.cli start --smoke` | 启动后再打一发真请求（`/health`、`/v1/chat`、`/v1/audit/<key>`），确认「进程在」等于「能答」 | 同上 |
| `python -m ops.cli stop` | 一键停止：**依赖逆序**、优雅优先、校验端口释放与无孤儿进程 | 同上 |
| `python -m ops.cli stop --force` | 直接强杀进程树（用于服务卡死不响应停机请求时） | 同上 |
| `python -m ops.cli restart` | 先停后起（等价于 stop + start，但一次调用完成） | 同上 |
| `python -m ops.cli status` | 列出所有登记服务：未运行 / 运行中(PID) / 状态文件残留 / 健康详情 | 同上 |
| `python -m ops.cli logs api -n 50` | 看某服务的日志尾部 | 0 |
| 任意命令加 `--json` | 机器可读输出（每条含 service/action/ok/message/advice） | 同上 |

临时改端口/主机/超时（不改配置文件）：`--port 18081 --host 127.0.0.1 --timeout 45 --stop-timeout 15`。
`--only api,ollama` 覆盖本次编排的服务集合。

## 二、服务清单与配置

服务集合、端口、是否接管外部进程全部来自 `.env`（不写在代码里）：

| 配置项 | 默认 | 含义 |
|---|---|---|
| `OPS_SERVICES` | `api` | 本次要编排哪些服务，逗号分隔 |
| `APP_HOST` / `APP_PORT` | `127.0.0.1` / `8080` | HTTP 服务监听地址。默认只绑回环，不对局域网开放 |
| `DRAIN_SECONDS` | `5` | 优雅停机时等待在途请求结束的上限 |
| `OLLAMA_TAKEOVER` | `0` | 是否由编排器负责起/停本机 `ollama serve`。**默认不接管**：只探测，不动你自己的进程 |
| `OLLAMA_BIN` | `ollama` | 接管时用的可执行文件名或绝对路径 |
| `LLM_PROVIDER` | `template` | 影响预检：选 `ollama`/`openai` 但配置不全时，启动会被**阻塞**并给出退路建议 |

已登记的服务：

| 名称 | 类型 | 端口 | 依赖 | 停止方式 |
|---|---|---|---|---|
| `api` | 本项目子进程（`python -m src.server`） | `APP_PORT` | — | `POST /admin/shutdown`（带一次性令牌）→ 自机关闭 |
| `ollama` | 外部进程（可选） | 11434 | — | 只有 `OLLAMA_TAKEOVER=1` 且是我们起的才接管停止 |

## 三、启动时序（`start`）

```
1 预检（全部目标服务，任一阻塞项 → 一个都不启动，直接退出）
    ├─ 端口是否可用（被外部进程占用 → 阻塞，并给出 netstat/ss 查占用方的命令）
    ├─ provider 配置是否自洽（ollama 不可达 / openai 缺密钥 / 未知 provider → 阻塞）
    └─ run/ 与 logs/ 与数据目录是否可写；合成店铺库是否存在（不可写 → 阻塞）
2 若检测到已在运行（状态文件 + pid 存活）→ 走一遍 stop（逆序），确认全部停止
3 轮转超大日志（>2MB 归档为 .log.1）
4 按依赖顺序 spawn 子进程（stdout/stderr 重定向到 logs/<name>.log，独立进程组）
5 写 run/<name>.json（pid / pgid / port / 是否我们起的）与 run/<name>.token
6 健康轮询直到 ready 或超时（默认 30s）：先比 pid，再看端口，再 GET /health 要求 status=ok
7 健康失败 → 回滚：终止该进程、清状态文件、fail-fast 中止后续服务
```

`start --smoke` 在 7 之后追加一次真调用链验证，成功输出长这样（实测）：

```
✅ [start] api：启动成功（PID 231844，用时 0.6s）｜provider=template｜检索=20 个二级意图｜规则版本=945a75946ecf
✅ [smoke] api：GET /health → 200
✅ [smoke] api：POST /v1/chat → 200｜意图=ORDER_STATUS｜门禁=['pass']｜人工出口=True｜引用=['tool:query_order#8a7a431b6d1b78a1']
✅ [smoke] api：GET /v1/audit/<key> → 200｜反查到规则版本 945a75946ecf
```

## 四、停止时序（`stop`）与资源释放

逆序（依赖者先停），每个服务走**升级阶梯**，能优雅就不暴力：

```
1 读 run/<name>.json
    ├─ 没有状态文件 → 报「未在运行」，仍然做一次端口校验（防止外部残留）
    ├─ 状态文件损坏 → 报错并给出「手工删除哪个文件、先确认哪个端口」的建议，绝不乱杀进程
    └─ pid 已死 → 只清残留状态（cleanup），不动别的
2 让服务自己关：api 用 POST /admin/shutdown + X-Ops-Token（令牌来自 run/api.token）
3 等进程退出（stop_timeout，默认 10s）
4 没退 → SIGTERM / taskkill（不带 /F）→ 再等
5 还没退 → kill_tree：POSIX `killpg(SIGKILL)`，Windows `taskkill /T /F` → 再等
6 校验三件事，缺一不算停干净：
    ① 进程真的不在了（无孤儿）② 端口已释放 ③ 状态文件与令牌文件已清理
```

服务自己那一侧的收尾（`src/server.py`，收尾动作只在主线程做一次）：

```
置 stopping 标志 → serve_forever 立即停止接新请求（在途的返回 503）
→ 等在途请求归零（最多 DRAIN_SECONDS，用引用计数而不是 sleep 猜时间）
→ server_close() 释放监听 socket
→ Application.close()：审计连接 commit 后关闭 + 工具层线程池 shutdown
→ 删除 run/api.token → 打印「收尾完成」→ flush stdout → 退出
```

数据与脏状态的处理口径（写清楚，不粉饰）：

- **已 commit 的审计行不会因停机丢失**；SQLite 每轮请求即时提交。
- 若在途请求超过 `DRAIN_SECONDS` 仍未结束，服务会继续关闭，日志明确写
  「尚未 commit 的那一轮不会落库」——那一轮就是丢了，不会假装无损。
- 用 `--force` 强杀时同样只可能丢掉正在处理中的那一轮；已落库数据与哈希链不受影响
  （哈希链会在下一次 `/health` 自检时暴露断点，不会静默）。

实测一次起停的输出（`--port 18082`）：

```
✅ [stop] api：已停止（PID 225800，方式：服务自机关闭）
✅ [cleanup] api：端口 127.0.0.1:18082 已释放
✅ [cleanup] api：无孤儿进程（PID 225800 及其子进程已回收）
```

## 五、健康检查语义

`GET /health` 返回的不只是「活着」，而是「能不能接流量」：

```json
{"status": "ok|unhealthy", "uptime_s": 12.3, "provider": "template",
 "kb": {"backend": "bm25", "backend_note": "内置 BM25（纯标准库实现）", "entries": 16, "stale_events": {}},
 "ruleset_version": "945a75946ecf", "shop_content_sha256": "9a75868c…",
 "components": {"shop_db": {"ok": true, "orders": 14, "kb_entries": 16},
                "audit_db": {"ok": true, "rows": 8, "chain_ok": true, "chain_broken_at": null},
                "intents":  {"ok": true, "l1": 3, "l2": 20, "high_risk": 4}},
 "counters": {"requests": 8, "commit_blocked_pre": 0, "commit_blocked_post": 0,
              "handoff_forced": 0, "degraded": 0, "errors": 0}}
```

- 编排器要求 `status == "ok"` 才算 ready；`unhealthy` 会把 `reason` 或失败的组件原样报给你。
- `audit_db.chain_ok` 是服务自己每 2.5s 级探活时顺带校验的哈希链——并发写把链写断这种事，
  靠这一项就能在 `/health` 里看见（测试 `test_http_concurrent_requests_are_serialised_correctly` 就是这么断言的）。
- `ruleset_version` 变化 = 有人改了白名单/词典/紧急词表/意图体系，运维上等于「规则换版」。

## 六、HTTP 接口契约（输入 → 输出）

| 端点 | 输入 | 输出 / 错误码 |
|---|---|---|
| `GET /` | — | 200 端点自述 |
| `GET /health` | — | 200（见上）；启动期未就绪时编排器按失败处理 |
| `GET /metrics` | — | 200 `{counters, gate_actions, tool_statuses, kb, uptime_s}` |
| `POST /v1/chat` | `{"text": "…1–500 字，必填", "session_id": "≤64 字，可选", "client_request_id": "可选"}` | 200 完整响应体（`request_key/reply/intent/confidence/must_handoff/gate_actions/decisions/handoff/citations/tool_calls/degraded/replayed/answerable/latency_ms/token_estimate`）；400 非法 JSON；413 请求体 >64KB；422 缺 text / 超长 / session_id 非法；500 内部错误并返回 `trace_id`（栈写在 `logs/api.log`）；503 正在停机 |
| `GET /v1/audit/<request_key>` | — | 200 反查（规则版本、条文版本、工具证据、决策链、重放计数）；404 未知 key |
| `POST /admin/shutdown` | 请求头 `X-Ops-Token`（= `run/api.token`） | 202 后开始收尾；401 令牌不对（**不会**停机） |

500 的响应体只给 `trace_id`，堆栈留在日志——不把内部栈往外吐。

## 七、异常场景与恢复建议（编排器实际会给的话）

| 场景 | 你会看到 | 恢复建议（就是它给的话） |
|---|---|---|
| 端口被外部进程占用 | `[阻塞] 端口 127.0.0.1:8080 被其它进程占用（不是本编排器登记的 api）` | 改 `.env` 的 `APP_PORT`，或用 `netstat -ano \| findstr :8080` / `ss -lntp` 找占用方自行决定；编排器**不会杀不属于它的进程** |
| provider 选了 ollama 但服务没起 | `[阻塞] LLM_PROVIDER=ollama，但 http://127.0.0.1:11434 无响应` | 起 `ollama serve`（或 `OPS_SERVICES=ollama,api` + `OLLAMA_TAKEOVER=1`）；只想离线跑就改回 `template` |
| 选了 openai 但缺密钥 | `[阻塞] LLM_PROVIDER=openai，但 OPENAI_API_KEY/… 未配齐` | 补齐三项或改用 template/ollama |
| 子进程起来就崩 | `[start] api 启动后健康检查未通过：进程已退出（PID …）。日志尾部：…` | 直接看它贴出的日志尾部；再单点复现 `python -m src.server --port 18099` |
| 服务卡死不接受停机 | `[stop] 进程 12345 在 10s 内没有退出` | 加 `--force`；或按它给的命令手动收进程组 |
| 停机后端口仍监听 | `[cleanup] 端口 … 仍在监听` | 说明另有进程占着（不是刚停的这个），给的是查占用方的命令 |
| 状态文件损坏 | `[cleanup] 状态文件损坏，无法确认进程归属` | 给出具体的删除路径，并要求先确认端口归属 |
| 依赖成环 | 直接抛 `服务依赖成环：x` | 编排器拒绝猜测顺序，改配置去环 |

## 八、日志

- 位置：`logs/api.log`、`logs/ollama.log`；子进程的 stdout+stderr 合并写入，行内带 `[api]` 前缀，
  访问日志与错误堆栈都在同一处，不用拼两个文件。
- 轮转：启动前若超过 2MB，归档为 `api.log.1`（保留一份旧的，不无限堆）。
- 停机收尾日志是可核对的：`收到停机请求 → 收尾完成：端口已释放、审计连接已关闭、临时文件已清理`。
  测试里有一条断言：**日志里不允许出现 `Fatal Python error`**——早先让后台线程做收尾+打印时
  确实撞到过解释器 finalize 抢 stdout 的脏退出，这条断言就是那次踩坑留下的哨兵。

## 九、如何新增服务（抽象层就四个方法）

```python
class MyService(ServiceSpec):                 # ops/services.py
    name = "worker"; title = "离线批处理"; depends_on = ()

    def preflight(self, ctx) -> list[Problem]: ...   # 不能起就返回带 advice 的 Problem
    def start(self, ctx) -> Started | None:    ...   # 不接管时返回 None
    def health(self, ctx, state) -> Health:    ...   # ready=True 才算接流量
    def graceful_stop(self, ctx, state) -> bool:...  # False = 交给编排器升级强杀
```

然后 `build_registry()` 里注册 + `.env` 的 `OPS_SERVICES` 加上名字。编排器不需要改：
停止顺序、状态文件、日志轮转、端口与孤儿校验、失败回滚都是它统一做的。
`tests/test_ops.py` 里的 `Fake`/`Stubborn` 两个假服务就是这么接进去验证顺序与强杀的，可以照抄。

## 十、有意不做的三件事（写清边界，避免被当成做到了）

1. **不做守护重启循环**：崩了就报失败并给日志，不自动拉起。自动拉起会把「配置错了」
   伪装成「服务偶尔不稳定」，在作品集项目里是负资产。
2. **不做开机自启/系统服务注册**（Windows 服务、systemd、supervisord 一律不碰）：
   那会改你的机器状态，且无法用一条命令可复现地验证。
3. **不做并发容量结论**：`/health` 与测试里只做 8 路并发正确性检查（哈希链、计数不丢），
   不给吞吐/容量数字——方案 §1.3 明确不做峰值容量。

## 十一、这套编排本身怎么被验证（真起真停，不是 mock）

```bash
python -m pytest tests/test_ops.py          # 21 条，约 47s（真的 spawn、真的占端口、真的停）
python -m ops.cli check                       # 看预检与当前状态
python -m ops.cli start --smoke --port 18081  # 一键启动 + 一发真请求
python -m ops.cli stop --port 18081           # 一键停止 + 三项残留校验
python scripts/mutation_test.py --only M11 M12  # 把「端口校验」「探活」故意做坏 → 用例必须变红
```

覆盖点：端口探测一致性、`pid_alive` 只读（Windows 上不能用 `os.kill(pid,0)`，那会顺手杀进程）、
预检阻塞时不留状态文件、起停全链路无残留、二次 start 走「先停后起」、僵尸状态文件只清理不误杀、
顽固服务升级到强杀、依赖顺序与逆序停止、依赖成环被拒、HTTP 契约与错误码、
并发 8 路写审计后哈希链仍完好、日志轮转。
